# Support access: owners and admins look after members' computers

Some members don't set up their own computers and connections. A team's
owners and admins look after them: they wake, delete and add a member's
cloud computers, install harnesses on them, and see and remove a member's
connections. They act on the member's things, never as the member.

The option is `create_app(admin_support_access=True)`, off by default. It
needs accounts mode, which has the team. Off, every host and connection is
its owner's alone, as in Omnigent without teams.

## The rules

- **Who.** Every active owner and admin, on everyone else's things.
- **Only from a browser.** The caller must be signed in through a browser or
  a trusted proxy (`Principal.is_interactive_human`). A CLI login, device
  grant, runner or host never gets support access.
- **Ownership never moves.** A computer added for a member is the member's
  row. Its provider is called with the member's owner context, read from the
  server's records (`sandbox_owners`), so a provider that binds each computer
  to one person sees the member, never the admin.
- **Logins stay the person's own.** No owner or admin starts, finishes or
  enters a subscription, MCP, GitHub or harness login for someone else. A
  provider's terms tie a login to the person who holds it, so a login made for
  someone else is a login they didn't make. An admin sees whether the member is
  signed in or connected, and may remove a connection, for example to clear a
  broken one before the member connects again.
- **Logged.** Every support action writes one line naming the acting member,
  the member acted for and what it touched, by member id and never by
  username or address (`omnigent.server.support_access`).

## Checked when it writes

A request checks the actor and the member when it starts, and again where it
acts, so a role change, suspension or removal that commits in between is seen.

- **Each write** (adding a computer, deleting one, removing a connection)
  checks them inside its own transaction (`authorize_support_action`), in the
  team's lock order:
  1. the team;
  2. the accounts, the actor's and the member's, whose registration must still
     be the one the request read with the membership;
  3. the member's membership, which must be the same member ID in an allowed
     state;
  4. the actor's, still an active owner or admin.
- **A command sent to a host after a wait,** such as a harness install on a
  computer that had to wake first, reads them again just before it is sent.

## Hosts

`may_manage_host` sits beside `resolve_host_owner`. It allows the host's
owner, or an owner or admin as above on a host whose owner is an active or
suspended member. It applies to:

- the host read and the persistent host's start and delete;
- harness install and the readiness refresh;
- model options and the detected sign-ins read.

Everything else on a host stays its owner's through `resolve_host_owner`:
harness credential writes, files, worktrees, runner launch and binding, a new
thread on the host, and the inventories (skills, plugins, MCP servers).

`POST /v1/hosts` takes `owner_user_id` from an owner or admin, naming an
active member. The write is pinned to the member's current registration.

A suspended member's computer can be read and deleted. It can't reconnect
until the member is reinstated, because the launch token of a suspended
owner's host is refused, so the member's page offers no Wake for it.

## A member's page

Under `/v1/team/members/{member_id}`, mounted only with the option:

| Route | What it does |
| --- | --- |
| `GET …/hosts` | The member's hosts, as their own `GET /v1/hosts` lists them |
| `GET …/connections` | For each MCP service the member may use and each connection provider (GitHub, …), whether they are connected; never a login |
| `DELETE …/connections/{provider}` | Removes the member's connection to a provider |
| `DELETE …/mcp-services/{service_id}/connection` | Removes the member's login to an MCP service, and any sign-in they had started |
| `GET …/threads` | The threads they own; for a removed member, their removal's record |

The member comes from the path alone. There is no connect route, and the
OAuth callback still binds a login only to the person who started it.

`GET /v1/team` reports `support_access`. The web page then shows Manage on
each other member's row, which opens `/settings/members/<member id>`: their
computers (state, Wake, Delete, Add a computer for them, and Manage, which
opens the provider's page for the computer, same-origin only, or its
overview), their connections with Disconnect, their threads, and their
account actions.

## Reset password

Reset follows suspension, with or without the option: an owner resets
anyone's password, an admin resets members' and their own. One write checks
the roles as they are then and changes the password
(`SqlAlchemyAccountStore.reset_password`). An account without a membership is
as before.

## Not here

A list on the member's own page of what admins did there (the log lines carry
what it needs), signing in for someone, other per-person data (agents,
schedules, preferences, projects), starting a thread on a member's computer,
and connections the whole team shares.
