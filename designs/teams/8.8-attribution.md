# Attribution of turns and approvals

A thread belongs to one person, a computer belongs to one person, and a
harness login belongs to the person whose computer it is on. A colleague with
edit access can still drive someone else's thread, so the work that thread
does runs on the owner's computer and login while someone else asked for it.
Every turn and every approval therefore records who did what on whose behalf,
in Omnigent's own records, as durable as the thread itself.

Attribution is a display, kept as best effort (D59). It never fails a turn,
refuses input or refuses an approval. Where it cannot tell, it says so ("not
certain", "assumed") rather than guessing silently.

## What a turn records

The user message that starts a turn carries its attribution, written in the
same insert as the message (`conversation_items.attribution`). The thread's
deletion deletes it; a copied thread keeps it, since it describes what
happened in the original.

| Field | Value | Source |
| --- | --- | --- |
| `initiator` | `person`, `schedule`, `agent` or `terminal`, with the person (or a schedule's owner), their account registration, the schedule or the sending thread, and for an agent the person it acts for | See below; never a runner's claim |
| `owner` | The thread's actual owner (a sub-agent's is its top thread's) | The single owner grant on the root thread |
| `host` | The computer, its name, its owner and kind (personal, cloud computer, sandbox), and the runner | The thread's host row; a sub-agent without its own runs on its top thread's |
| `subscription` | Whose configured harness login: the computer's owner, the provider family, and the login state the computer last reported | The host row; the login state is labelled as reported by the computer |
| `harness`, `model`, `effort` | Requested and last reported, `null` when unknown | The session's settings and the harness's own reports |

A provider account id is never known without reading a credential, so
`account` is always `null` and `verified` always `false`: the record says
"Alice's configured Claude login (provider account not verified)". A
provider the installation configured for a session (an inference snapshot)
is recorded as `configured_provider`, with no person as its subject. No cost
is recorded. No credential, sign-in code, access assertion or prompt content
appears in attribution.

## Who started a turn

The server decides from its own records:

| Path | Initiator |
| --- | --- |
| A person sends a message | `person`, from the request's sign-in |
| A scheduled task fires on a connected computer, or its saved prompt is delivered to a managed sandbox | `schedule`, its owner and task, from the task row and the saved input's origin |
| A runner posts a sub-agent's prompt, an agent returns a result into its thread, a thread messages another, or a blocked child wakes its parent | `agent`, for the person the server recorded as the turn actor of the thread the agent works for; with none recorded, the thread's owner (`owner_assumed`) |
| A web message to a terminal harness, recorded when the transcript mirrors it | The sender the server recorded durably when it accepted the message (see below), on any replica and after a restart |
| A prompt typed into a terminal harness | `terminal`: whoever sent input to the thread's terminals since the turn (or the previous typed prompt) started. Several possible typists are all named (`possible`) and the prompt is marked not certain; with no typing the server saw (a direct local attach), the computer's owner, recorded as assumed |

A runner's `created_by` is never taken. Before this change a runner could
name any person with edit access as a message's sender, and that name became
the thread's turn actor, which policies, the MCP gateway and approvals read.
Now the server derives the person itself and uses that for the item's
author, the turn actor and the attribution alike. One edge case follows: a
sub-agent is attributed to the parent's turn actor at the moment its prompt
arrives, so if Bob sends a message to the parent while Alice's turn is
creating a child, the child's prompt can be attributed to Bob.

## Who took part in a turn

The server keeps a durable record of who sent input to a thread, the same on
every replica and after a restart. Each write is best effort: a failed write
is logged and the input or turn goes ahead.

**Every accepted input is recorded** (`session_inputs`) with the person
answerable for it: a forwarded message under its persisted item id, a message
queued for a terminal harness under its server-issued pending id, with a
digest of its text. When the harness's transcript records the message, the
transcript item is mapped to it. If the queued entry in memory is gone (a
restart, another replica), the record is claimed by its text in one write
transaction, so two replicas never take the same record. When several people
sent the same text, every one of them is named as possible and the message
reads as not certain. A message that was definitely never delivered stops
matching by text, so an identical later message is attributed to its own
sender.

**Turns are registered beside the harness** (`session_turns`). A runner that
advertises `turn_inputs` posts `POST /v1/sessions/{id}/turns` with the
server-issued ids of the inputs the turn starts with. The harness never waits
for it: the request runs alongside the turn, is retried twice with the same
turn id (which the server treats as the same turn), and is logged if it
cannot land. The server reads the inputs' senders from its own records and
names the turn's person on the thread (`omnigent.turn_actor`, which policies
and the MCP gateway read). Only the runner currently bound to the thread may
register. An id that names no record leaves the turn's person unknown. A
recovery or continuation turn names no inputs and keeps the current turn. A
runner without the capability keeps the older forward-time record.

**Typing is recorded per terminal and person** from the authenticated attach
connection, alongside the keystrokes and never ahead of them: through the
runner proxy on every Enter and at most once a second while typing; through
the server's in-process bridge, whose frames it does not inspect, at most once
a second. A failed record is logged; the input is never delayed or refused.
Attachment alone records nothing.

**Who took part** in the current turn is read with no cap: the turn's own
inputs, and every input accepted and all terminal typing since it was
registered. A message queued behind a running turn counts as part of it (a
non-native harness can inject it), and so does every possible typist. With
no registered turn (a registration still in flight or lost, or an older
runner), only the thread's recorded turn actor is named; the thread's history
is not scanned.

## Approvals

The approval ledger (WP8.6) already binds the asking principal, initiator,
owner, action, destination and a digest of the decision. Each ledger row now
also records, in the same insert, who asked: the turn's initiator and
contributors, the asking principal, and the thread's owner, computer and
login as for a turn. `authority.complete` is `false` when the record of who
took part could not be read. Each answer records the grant it was given
under: `thread_owner`, `thread_approver`, `service_approver` or
`team_approver`.

Omnigent's approvals record a person's consent. They are not a
separation-of-duties control. Where an action needs several people's eyes,
the external system enforces it, for example GitHub's required pull-request
reviews and branch protection. The person who started an action may
therefore approve it by default (D59). A resource can turn that off (WP8.6);
it then excludes the people this record names, as best effort. An incomplete
or unreadable record only narrows that exclusion to the people it does name.
No answer is refused because of it, including answers to approvals that were
pending before this change.

Answered rows are kept until their thread is deleted and are deleted with it
(including its sub-agents'). Unanswered rows keep 8.6's purge a week after
expiry.

## Known gaps

These paths can leave a person out of a turn's record. Each is a display
limit and, where a resource has turned off approval by the initiator, a
narrower exclusion; none is a security boundary (see Approvals).

- **Registration timing.** The harness does not wait for its turn's
  registration. Until it lands, and for a whole turn whose registration could
  not land, the thread's turn actor (which policies, the MCP gateway's policy
  attribution and approvals read) is still the previous turn's person.
- **Delayed delivery.** An input accepted before a turn was registered but
  injected into it later is not counted among that turn's contributors.
- **Child, peer and wake inputs.** A sub-agent's prompt, a message between
  threads, and a child waking its parent carry one person from the source
  turn (its turn actor), not its other contributors or its uncertainty.
- **Codex side chats.** A follow-up to a Codex `/side` child goes straight to
  the parent runner; it is neither recorded as an input nor registered as a
  turn, and its transcript is attributed to the parent's turn actor.
- **Terminal typing the server does not see.** Typing through the runner's
  direct local attach never reaches the server; until its transcript record
  arrives (then recorded with the computer's owner as the assumed typist) it
  is not counted. A typing record that fails or is still in flight is missed
  too, through the proxy and the in-process bridge alike.
- **History recovery.** A persisted message the runner recovers from history
  runs without a registration, and if its input record failed to save, its
  sender is not named.
- **Runner choice.** The runner chooses which of the thread's real inputs it
  names when it registers. A runner altered to name a later input could start
  the window late; it cannot name a person or another thread's input.
- **Sub-agent timing.** A sub-agent is attributed to its parent's turn actor
  when its prompt arrives, so a message Bob sends to the parent while Alice's
  turn creates a child can attribute the child's prompt to Bob.
- A message typed in the terminal while a registered turn runs extends that
  turn's contributors; it does not start a new turn.

## API and display

- Items: `attribution` on the user message that starts a turn, with `null`
  for unknown values; also on `session.input.consumed`.
- `GET /v1/sessions/{id}/approvals` lists a thread's approvals, its
  sub-agents' included, for anyone who can read the thread;
  `GET /v1/sessions/{id}/approvals/{eid}` reads one, also for the approvers
  named to answer it. Both are for people only. `GET /v1/approvals` and the
  resolve response (to the person who answered) carry the same record; the
  generic elicitation read, which runners use, does not.
- `POST /v1/sessions/{id}/turns` registers a turn (the bound runner only),
  as best effort beside the harness.
- The chat shows one line per turn: "bob, on alice's computer and alice's
  Claude subscription", with the full record in its tooltip. It sits in the
  transcript when someone other than the computer's owner started the turn,
  or a schedule or an agent did; otherwise in the message's hover row.
- Approval cards and the approval page show "Asked during alice's turn, on
  alice's computer (bob also sent input to this turn)" and "Approved by carol
  as an approver for the service", read through the authorized endpoint.
- Ambiguous terminal typing reads "alice or admin in the terminal (not
  certain)".

The history of a thread's approvals as a page belongs to the user-manual
journey (8.10).

## A separately hosted conversation database

Conversation tables can live on their own database, which is created by
`create_all` and never migrated. One created before this change has no
`attribution` column. The store checks once at start: without the column it
neither writes nor reads attribution, and every turn's attribution reads as
unknown. No turn fails for it. Adding the column (`ALTER TABLE
conversation_items ADD COLUMN attribution TEXT`) turns it on at the next
start.
