# Attribution of turns and approvals

A thread belongs to one person, a computer belongs to one person, and a
harness login belongs to the person whose computer it is on. A colleague with
edit access can still drive someone else's thread, so the work that thread
does runs on the owner's computer and login while someone else asked for it.
Every turn and every approval therefore records who did what on whose behalf,
in Omnigent's own records, as durable as the thread itself.

## What a turn records

The user message that starts a turn carries its attribution, written in the
same insert as the message (`conversation_items.attribution`). The thread's
deletion deletes it; a copied thread keeps it, since it describes what
happened in the original.

| Field | Value | Source |
| --- | --- | --- |
| `initiator` | `person`, `schedule`, `agent` or `terminal`, with the person (or a schedule's owner), their account registration, the schedule or the sending thread, and for an agent the person it acts for | See below; never a runner's claim |
| `owner` | The thread's actual owner (a sub-agent's is its top thread's) | The single owner grant on the root thread |
| `host` | The computer, its name, its owner and kind (personal, cloud computer, sandbox), and the runner | The thread's host row; a sub-agent without its own runs on its top thread's |
| `subscription` | Whose configured harness login: the computer's owner, the provider family, and the login state the computer last reported | The host row; the login state is labelled as reported by the computer |
| `harness`, `model`, `effort` | Requested and last reported, `null` when unknown | The session's settings and the harness's own reports |

A provider account id is never known without reading a credential, so
`account` is always `null` and `verified` always `false`: the record says
"Alice's configured Claude login (provider account not verified)". A
provider the installation configured for a session (an inference snapshot)
is recorded as `configured_provider`, with no person as its subject. No cost
is recorded. No credential, sign-in code, access assertion or prompt content
appears in attribution.

## Who started a turn

The server decides from its own records:

| Path | Initiator |
| --- | --- |
| A person sends a message | `person`, from the request's sign-in |
| A scheduled task fires on a connected computer, or its saved prompt is delivered to a managed sandbox | `schedule`, its owner and task, from the task row and the saved input's origin |
| A runner posts a sub-agent's prompt, an agent returns a result into its thread, a thread messages another, or a blocked child wakes its parent | `agent`, for the person the server recorded as the turn actor of the thread the agent works for; with none recorded, the thread's owner (`owner_assumed`) |
| A web message to a terminal harness, recorded when the transcript mirrors it | The initiator the server stored with the queued message |
| A prompt typed into a terminal harness | `terminal`: the person attached to that terminal with typing rights (the owner, or an administrator under the human override); with nobody attached on this server, the owner, recorded as assumed |

A runner's `created_by` is never taken. Before this change a runner could
name any person with edit access as a message's sender, and that name became
the thread's turn actor, which policies, the MCP gateway and approvals read.
Now the server derives the person itself and uses that for the item's
author, the turn actor and the attribution alike. One edge case follows: a
sub-agent is attributed to the parent's turn actor at the moment its prompt
arrives, so if Bob sends a message to the parent while Alice's turn is
creating a child, the child's prompt can be attributed to Bob.

## The turn actor follows turns, not messages

The thread's turn actor (`omnigent.turn_actor`) is the person approvals,
policies and the MCP gateway treat as an action's initiator. It used to be
written when a message was forwarded, so a message Bob queued behind Alice's
running turn relabelled that turn as Bob's: an approval asked during Alice's
turn named Bob, and Alice, as a named service approver, could approve her
own action where self-approval is off. Terminal harnesses never recorded it
at all, so their approvals named the owner whoever sent the turn.

The runner now advertises `turn_inputs` and publishes
`session.turn_started` whenever it starts a turn, naming the inputs the turn
starts with: the persisted item ids of forwarded messages, or the stable ids
of messages queued for a terminal harness. It names inputs, never people.
The relay reads each input's attribution (or the sender stored with the
queued message) and records the turn's person and start time
(`omnigent.turn_started_at`). Ids that name nothing in this thread are
ignored, and a report with nothing verifiable changes nothing. A turn with
no inputs (a recovery or a continuation) keeps the current person. A
runner without the capability keeps the forward-time record.

A message can also join a running turn: a non-native harness injects a
queued message into the turn in progress. So an approval records, besides
the turn's initiator, everyone whose input entered the thread since the turn
started (`contributors`). Where the person who started an action may not
approve it, none of them may. The window can include more people than
strictly steered the action (a queued message not yet injected; input saved
in the same second the turn started), never fewer.

Limits:

- The runner chooses which of the thread's real inputs it names. A runner
  altered to name a later input could start the window late; it cannot name a
  person or an input from another thread.
- A message to a terminal harness without a stable id, or whose queued entry
  lives on another server replica, cannot be matched at turn start; the turn
  keeps the previous person while the window keeps growing.
- A prompt typed into a terminal changes the turn actor but not the turn's
  start, since no runner dispatch started it.

## Approvals

The approval ledger (WP8.6) already binds the asking principal, initiator,
owner, action, destination and a digest of the decision. Each ledger row now
also records, in the same insert, who asked: the turn's initiator and
contributors, the asking principal, and the thread's owner, computer and
login as for a turn. Each answer records the grant it was given under:
`thread_owner`, `thread_approver`, `service_approver` or `team_approver`.

Answered rows are kept until their thread is deleted and are deleted with it
(including its sub-agents'). Unanswered rows keep 8.6's purge a week after
expiry.

## API and display

- Items: `attribution` on the user message that starts a turn, with `null`
  for unknown values; also on `session.input.consumed`.
- `GET /v1/sessions/{id}/approvals` lists a thread's approvals, its
  sub-agents' included, for anyone who can read the thread; people only.
  `GET /v1/approvals`, `GET .../elicitations/{eid}` and the resolve response
  carry the same approval record.
- The chat shows one line per turn: "bob, on alice's computer and alice's
  Claude subscription", with the full record in its tooltip. It sits in the
  transcript when someone other than the computer's owner started the turn,
  or a schedule or an agent did; otherwise in the message's hover row.
- Approval cards and the approval page show "Asked during alice's turn, on
  alice's computer (bob also sent input to this turn)" and "Approved by carol
  as an approver for the service".

The history of a thread's approvals as a page belongs to the user-manual
journey (8.10).

## A separately hosted conversation database

Conversation tables can live on their own database, which is created by
`create_all` and never migrated. One created before this change has no
`attribution` column. The store checks once at start: without the column it
neither writes nor reads attribution, and every turn's attribution reads as
unknown. No turn fails for it. Adding the column (`ALTER TABLE
conversation_items ADD COLUMN attribution TEXT`) turns it on at the next
start.
