# Machine principals and route authority: inventory and plan

A runner and a host act for one person. Before this change a runner held a
short-lived copy of its owner's session JWT (marked `delegated=runner`), so
every check that looked only at the user id treated it as that person,
including the administrator override on other people's threads. Personal
hosts also handed their own sign-in to the runners they launched.

This document lists every surface that carries authority, classifies who may
use it, and splits the work into two reviewable changes.

## Principals

| Kind | Credential | Acts for |
| --- | --- | --- |
| Human | Browser cookie, CLI login, login grant, trusted proxy header | The person |
| Delegated client / service | Device grant or client-credentials token (`scope` claim) | Unchanged: their existing path allowlist |
| Runner | Runner token minted from the runner's binding token | The thread's owner, through one runner incarnation |
| Host | Launch token (managed host) or the person's login (personal host) | The host's owner |

Rules for machine principals (runner, host):

- Minted only from the current server-side binding (runner → thread → owner,
  thread → host → host owner). Nothing a caller supplies chooses the owner.
- Never an administrator. The override that lets a human admin open any
  thread stays for humans and is never applied to a machine principal.
- Own audience. A runner token is not a session cookie, cannot sign in, cannot
  be exchanged for a grant, and is refused under `/auth` and `/oauth`.
- Bound per request. A runner token is accepted only while its thread is still
  bound to that runner on that host, for that account registration.
- Owner-only on threads. A runner reaches threads its person owns; share and
  public grants do not apply to it until a session-targeted capability exists.

## Inventory

`H` = human only, `R:<scope>` = humans and runners holding that scope,
`P` = the guard admits any caller because the route authenticates itself or
needs no identity. Unauthenticated requests always pass the guard; the route's
own check answers them. Host principals have no HTTP token yet (see 8.2b and
the device work), so the only host surfaces are route-authenticated.

### Other authority

| Surface | Today | Plan |
| --- | --- | --- |
| Token mint and refresh | Owner JWT, `delegated=runner`, 30 min | 8.2a: runner token from the binding; legacy tokens refused |
| Runner launch admission (`admit_launch`) | Checks host owner, not thread owner | 8.2a: a thread owned by someone else, or by several people, is refused; accounts mode already requires an owner |
| Accounts-mode mint lock (`with_runner_authority`) | First owner grant, any host owner | 8.2a: single owner, host owned by that owner |
| Runner resume and replacement | Binding rewritten before launch | 8.2a: token dies with the binding; stale-result rejection is 8.2b |
| Schedules | Owner checked at create; fire uses server context | 8.2b |
| Sub-agents | Children inherit the parent runner | 8.2b: lineage-bounded child authority |
| Files, artifacts, previews | Session ACL plus owner bar for absolute paths | 8.2a: owner-only for runners; 8.2b: object-id binding and stream revocation |
| MCP connection use | Caller's own connection on a thread they can edit | 8.2a: runner must own the thread |
| Host credential broker | Launch token, host owner | Unchanged |
| Owner display | First owner grant | 8.2a: the single owner, none when ambiguous |

## Split

**8.2a (this change):**

1. Principal type with machine fields (registration, host, thread, runner,
   audience, expiry, token id, scopes) and the runner token: mint and refresh
   from the binding, per-request binding check, separate audience, legacy
   tokens refused.
2. Machine principals are never administrators: the permission store, the
   access helpers and the thread list apply owner-only access for them.
3. A central guard: every route is classified; an unclassified route or a
   missing scope fails closed. A test fails on any unclassified route.
4. The 8.1 call sites: `admit_launch` and `with_runner_authority` refuse a
   host owner who is not the thread owner; owner display is strict; runners
   lose the admin override everywhere (terminal attach, absolute paths, agent
   and MCP changes, owner actions, deletion).
5. Runners launched by a host use the runner token, not the host's sign-in,
   whenever the server offers runner tokens. A refused mint (401/403) stops
   the runner with the reason in its log and the session's error; no sign-in
   stands in. Only a server without runner tokens (404, or an explicit
   "unsupported" answer) keeps the old bootstrap.
6. Shared threads keep working: an editor's message runs on the owner's runner
   and host; the initiator, the thread owner and the acting principal are
   recorded separately in the request audit attributes.

**8.2b (next):** per-frame authority on runner and host tunnels, the thread
stream and terminal sockets (close on rebinding or revocation); schedule
reauthorization at fire and wake; sub-agent lineage and session-targeted
shared sends; file and artifact object binding and stream revocation; the
host HTTP token contract used by the device work.

## Tests (8.2a)

Two non-admin people (Alice, Bob), an administrator and the administrator's
runner: cross-user reads and writes through HTTP, list and search, the runner
tunnel and host tunnel handshakes; same-person positives; a stolen token on
another runner; a legacy `delegated=runner` token; wrong host, thread and
incarnation; expiry; route-inventory completeness.
