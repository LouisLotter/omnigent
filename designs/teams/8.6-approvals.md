# Approver roles, protected policies and verdict binding

Approval is its own authority. Reading, editing or managing a thread, and
being an administrator, do not let someone approve its actions. A person
approves their own work; named approvers answer for a thread, a service or the
team. Policies a runner or an agent bundle adds can make an action stricter
but cannot weaken the rules a person or the team's administrators keep.

## Who answers

Every policy ASK the server raises is recorded in the approval ledger with the
approvals it requires:

| ASK from | Answered by |
| --- | --- |
| An ordinary policy (session, agent, default, server config) | The thread's owner, or approvers named for the thread |
| The same, on a service that has named approvers | That service's approvers |
| A personal protected rule | Its person |
| A team protected rule | The approvers of the service the rule names, else the team's approvers |

Requirements accumulate: when an ordinary policy and a team rule both ask, the
person and a team approver must both accept. Any eligible decline declines.
By default the person who started an action may approve it on their own thread
but not on a service or for the team; an administrator can change that per
resource. Approvers named or removed after an ASK make it unanswerable; it
must be asked again.

Only a person signed in through a browser answers (a trusted proxy's identity
header counts the same way). The session cookie a browser sign-in sets carries
a mark the token returned to a CLI does not, so a stored CLI or host sign-in,
a login grant, a device grant, a client-credentials token and every runner or
host token are refused, through either answer route and over the runner
tunnel. A magic-link handoff from the CLI signs a browser in without the mark,
so approvals there need a password sign-in. Questions that are not approvals
(forms, plan reviews, harness permission prompts) keep their existing rules.

## Protected policies

Team rules (administrators) and personal rules (their person) are stored apart
from ordinary policies and use registered handlers. The engine runs them after
every ordinary policy, on the final arguments, with no labels, session state or
usage. They read server facts instead: owner, actor, initiator, phase, tool,
destination service and connection generation. Their label writes, state
updates and transforms are ignored, and a rule that cannot load or raises
denies. The decision is monotonic: a deny survives, every required approval
survives, an allow never removes an ask. Policies cannot write labels in the
server's `omnigent.` namespace, so the turn's initiator stays server-recorded.

This closes the bypass ADR 0004 records for anything expressed as a protected
rule. Ordinary policies, including administrators' default policies, still
share labels and state with each other; a rule that must hold belongs in the
protected domain.

## What a verdict is bound to

The ledger row binds, by digest: the requesting principal (kind, account,
runner, host), initiator, owner, thread, phase, tool, destination, the final
content, the service connection's generation (service version, login, login
creation), the runner connection's generation, the operation id, and
fingerprints of the protected rules and the approvers involved. It expires
after the prompt's timeout plus a short grace.

An approval is consumed by one conditional update that matches the recomputed
binding, so of concurrent retries exactly one runs the call. Changed arguments,
a later transform, a swapped tool, a changed rule or approver, a reconnected
service or runner, or expiry need a new decision. The MCP gateway checks the
protected rules once more on exactly what it is about to send, and records the
call's result on the approval: a retry of the same operation gets that result
instead of running again. The server-held native and request gates consume
the approval the same way before they allow.

The relay gate for runner-local tools records requirements and answers, but
the runner executes those tools itself; the server cannot consume on its
behalf. Protected guarantees hold where the server is the effect boundary.

## API (human administrators; writes need a browser sign-in)

| Route | Purpose |
| --- | --- |
| `GET /v1/approvals` | Pending approvals the caller may answer |
| `GET/POST/DELETE /v1/approvers` | Approvers of a thread, service or the team |
| `PUT /v1/approval-settings` | Whether the initiator may approve, per resource |
| `GET/POST/PATCH/DELETE /v1/protected-policies` | Team rules; personal rules by their person only |

An approver who cannot see the thread reads the prompt at
`GET /v1/sessions/{id}/elicitations/{eid}` and answers at its resolve URL.
