# Approver roles, protected policies and verdict binding

Approval is its own authority. Reading, editing or managing a thread, and
being an administrator, do not let someone approve its actions. A person
approves their own work; named approvers answer for a thread, a service or the
team. Policies a runner or an agent bundle adds can make an action stricter
but cannot weaken the rules a person or the team's administrators keep.

## Who answers

Every policy ASK the server raises is recorded in the approval ledger with the
approvals it requires:

| ASK from | Answered by |
| --- | --- |
| An ordinary policy (session, agent, default, server config) | The thread's owner, or approvers named for the thread |
| The same, on a service that has named approvers | That service's approvers |
| A personal protected rule | Its person |
| A team protected rule | The approvers of the service the rule names, else the team's approvers |

Requirements accumulate: when an ordinary policy and a team rule both ask, the
person and a team approver must both accept. Any eligible decline declines.
Whether the request is complete is decided under the ledger row's lock from
every answer recorded so far, so two approvers answering different
requirements at the same moment approve it, and exactly one of the two answers
resolves the prompt. By default the person who started an action may approve it
on their own thread but not on a service or for the team; the setting can be
changed per resource. A thread whose setting refuses its initiator refuses its
owner's own actions too: someone else must approve them. A thread's owner names the approvers for their own thread, since
that only adds people who may approve the owner's own work; an administrator
names a service's or the team's. Neither edit access nor the administrator
flag manages another person's thread. Approvers named or removed after an ASK
make it unanswerable; it must be asked again. Deleting an account removes its
approver grants and personal rules in the deletion transaction, and a deleted
account cannot be named, so a person who later registers the same username
inherits nothing.

Only a person signed in through a browser answers (a trusted proxy's identity
header counts the same way). The session cookie a browser sign-in sets carries
a mark the token returned to a CLI does not, so a stored CLI or host sign-in,
a login grant, a device grant, a client-credentials token and every runner or
host token are refused, through either answer route and over the runner
tunnel, with a message pointing to the web page. A browser session without
the mark (signed in before the upgrade, or through a link the CLI opened) is
told to sign in again in the browser. Questions that are not approvals
(forms, plan reviews, harness permission prompts) keep their existing rules.

A non-browser credential also cannot turn itself into a browser sign-in.
Resetting a password (which returns a password that signs anyone in) and
creating an invitation (which becomes a new sign-in, possibly an
administrator's) need a browser sign-in. A cookie reissued after a password
change keeps the provenance of the credential that changed it: only a browser
sign-in gets a browser-marked cookie back. Changing one's own password with
the old password still works from any client.

## Protected policies

Team rules (administrators) and personal rules (their person) are stored apart
from ordinary policies and use registered handlers. The engine runs them after
every ordinary policy, on the final arguments, with no labels, session state or
usage. A tool call always reaches them, and every enforcement site, in one
shape, `{"name": ..., "arguments": ...}`: a transform's output is the call's
new arguments. They read server facts instead of labels: owner, actor,
initiator, phase, tool, destination service and connection generation. The
initiator of a runner's action is the server-recorded turn actor, whatever
headers the runner sends. Their label writes, state updates and transforms are
ignored, and a rule that cannot load, raises or (for a handler that can report
it, such as CEL) cannot evaluate its expression denies. The decision is monotonic: a deny survives, every required approval
survives, an allow never removes an ask. Policies cannot write labels in the
server's `omnigent.` namespace, so the turn's initiator stays server-recorded.

This closes the bypass ADR 0004 records for anything expressed as a protected
rule. Ordinary policies, including administrators' default policies, still
share labels and state with each other; a rule that must hold belongs in the
protected domain.

## What a verdict is bound to

The ledger row binds, by digest: the requesting principal (kind, account,
runner, host), initiator, owner, thread, phase, tool, destination, the final
content, the service connection's generation (the service's version and the
login's id, which a reconnect replaces and a token refresh keeps), the runner
connection's generation, the operation id, and fingerprints of the protected
rules and the approvers involved. It expires after the prompt's timeout plus a
short grace.

An approval is consumed by one conditional update that matches the recomputed
binding, so of concurrent retries exactly one runs the call. Every change to
approvers or protected rules, and every consumption, first takes the team row
lock; the consumption rereads the approvers and rules under it, so a grant
removed or a rule changed before it commits refuses it on every backend.
Changed arguments, a later transform, a swapped tool, a changed rule or
approver, a reconnected service or runner, or expiry need a new decision.

Just before it sends, the MCP gateway evaluates the protected rules once more
on exactly that call. Every approval they require must be one the consumed
approval was given for, under the same rules and approvers; otherwise it asks
again. It checks that the service's login is still the approved one and pins
it, so the token read for the call refuses a login replaced in the meantime.
The call's result is recorded on the approval: a retry of the same operation
gets that result instead of running again. The server-held native and request
gates consume the approval the same way before they allow, and a re-posted
question reuses its recorded answer only while the principal, initiator,
owner, request, rules and approvers it was bound to are unchanged.

The relay gate for runner-local tools records requirements and answers, but
the runner executes those tools itself; the server cannot consume on its
behalf. Protected guarantees hold where the server is the effect boundary.

## API (writes need a browser sign-in)

| Route | Purpose |
| --- | --- |
| `GET /v1/approvals` | Pending approvals the caller may answer |
| `GET/POST/DELETE /v1/approvers` | Approvers of a thread (its owner) or of a service or the team (administrators) |
| `PUT /v1/approval-settings` | Whether the initiator may approve, per resource, managed the same way |
| `GET/POST/PATCH/DELETE /v1/protected-policies` | Team rules; personal rules by their person only |

An approver who cannot see the thread reads the prompt at
`GET /v1/sessions/{id}/elicitations/{eid}` and answers at its resolve URL.
