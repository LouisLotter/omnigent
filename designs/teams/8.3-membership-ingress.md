# Membership behind an identity-aware proxy (WP8.3)

A team's Omnigent often sits behind a proxy that signs people in before Omnigent
sees them: Cloudflare Access, a cloud IAP, an SSO gateway. Until now Omnigent
learned nothing from it. A person signed in at the proxy as Alice could carry
Bob's session cookie, and Omnigent would serve Bob. This change makes the
proxy's identity part of every request, binds it to one team member, and refuses
a credential that belongs to anyone else. It also adds the team page's API:
invitations, roles, suspension.

Everything here is off by default. A server without a proxy configured behaves as
before; the team API and suspension work without a proxy too.

## The envelope

The proxy signs, per forwarded request, `x-omnigent-external-identity:
v1.<payload>.<mac>`: base64url JSON `{v, iss, sub, aud, email?, owner, iat, exp}`
and an HMAC-SHA256 under a key the proxy and server share
(`OMNIGENT_EXTERNAL_IDENTITY_KEY`), over `"omnigent-external-identity/v1." +
payload`. The server checks the MAC before reading the payload, a lifetime of at
most 300 s, 30 s of clock skew, lowercase email, and optionally an expected
issuer and audience. The proxy must strip any envelope a client sends.

`owner` says the proxy recognised the installation's operator (for example an
owner pin matched). It is used once, to bind the existing owner account.

An HMAC envelope rather than the proxy's own JWT keeps the server
provider-neutral and avoids a certificate fetch from the server on every request;
the proxy has already validated its assertion.

## Modes

`OMNIGENT_EXTERNAL_IDENTITY_MODE`:

- `off` (default): the header is ignored.
- `bind`: an envelope, when present, must verify and must name the member whose
  credential the request carries. A request without one is unchanged. This is
  the step for moving an existing installation over: the owner binds on first
  entry.
- `required`: a person's credential (session cookie, bearer, login or device
  grant) is honoured only with an envelope, so people reach Omnigent only through
  the proxy. Runner and host tokens and anonymous requests are unaffected:
  machines that never pass the proxy keep working.

## The same-person rule

`ExternalIdentityMiddleware` runs inside authentication, so it knows the
request's principal. For each HTTP request and WebSocket handshake:

| Request | Answer |
| --- | --- |
| Envelope bound to member M, credential of account U | U must be M's account, else 403 `external_identity_mismatch`; M suspended: 403 `member_suspended` |
| Envelope not bound, carrying a credential | 403 `external_identity_unbound`, unless the owner binds (below) |
| Envelope not bound, no credential | Proceeds: sign-in and invitation pages, static files, public info |
| Bad envelope | 403 `external_identity_invalid` |
| No envelope, `required`, a person's credential | 403 `external_identity_required` |

The routes that establish a sign-in check the person themselves, because their
incoming credential is about to be replaced: `/auth/login` (only the bound
member's username; an unbound sign-in only for the owner's first entry or a link
invitation), `/auth/register` (a team invitation for the envelope's address),
`/auth/magic/redeem` (the link's account must be the bound member),
`/oauth/token` refresh (the grant's account must be the bound member),
`/auth/setup` and `/auth/logout`. OAuth callbacks, password changes and device
consent authenticate by the session cookie, so the central rule covers them.
Refusals name nothing about the other account.

## Binding

- **New member.** A team invitation names one address and a role. `POST
  /auth/register` with an envelope creates the account, an active membership and
  the binding (provenance `invitation`) in one transaction and consumes the
  invitation. The envelope's address must be the invited one; an identity
  already bound cannot take a second membership. Binding never happens by email
  alone: it also needs the invitation's token and an unbound subject.
- **Existing account.** An owner's link invitation names an account; the invitee
  proves it with its password at `/auth/login` (`invite` in the body), provenance
  `account_proof`.
- **The existing owner.** With `owner` set and the request carrying that active
  owner's own credential, the identity is bound (provenance `migration`). A pin
  claim with someone else's account binds nothing.

The binding keeps the address it was verified with (`team_identity_bindings.email`)
for the proxy's admission list. It is never an authorization key: a changed
address with the same subject is the same member; the same address with a new
subject is unbound.

## The team API

`GET /v1/team`, `POST /v1/team/invitations`, `DELETE
/v1/team/invitations/{id}`, `PUT /v1/team/members/{id}/role`, `POST
/v1/team/members/{id}/suspend` and `/reinstate`, and the public `GET
/v1/team/invitations/preview`. An owner invites admins and members, changes
roles, and suspends or reinstates anyone but themselves; an admin invites
members and suspends or reinstates members. The last active owner is kept.
Every change needs a browser sign-in, so runners, hosts, CLI sign-ins and device
grants cannot administer the team. Behind a proxy, inviting needs the caller's
own sign-in to be bound. Settings → Members shows the team when the server has
one.

## Suspension

`SqlAlchemyAccountStore.change_member_state` suspends in one transaction and
rotates the account's registration through the path a password reset uses:
sessions, refresh and device grants, magic links, runner and host tokens issued
before all die, and hosts, schedules and the membership move to the new
registration, so nothing is orphaned. `accepts_generation` also refuses a
suspended member, for every credential kind, so a fresh sign-in is refused too.
Open sockets and streams are woken at once (`authority_changes`) and re-check;
the 15–30 s re-check interval still bounds it in a multi-process server.
Scheduled fires of a suspended owner skip (`owner_suspended`) and stay enabled,
so reinstatement resumes them. A reinstated member signs in again in the browser
and on each laptop; cloud computers reconnect on their own.

## The proxy's admission list

`MembershipAdmission` is a deployment adapter that applies who the proxy admits:
active members' verified addresses and pending, unexpired invitations
(`AdmissionSnapshot`). Every change that alters the list commits a higher
`teams.admission_revision` first; `AdmissionSync` then pushes the snapshot,
retries with backoff and repeats hourly, so an expired invitation drops out. The
adapter applies a snapshot only when it is newer than the last one applied.
Omnigent's own checks never depend on it.

## Limits

- Several server processes: the wake reaches only the process that made the
  change; the regular re-check interval bounds the others.
- A login-time admin roster (`admins`) can still promote an account to admin
  without an owner; it is a deployment setting, empty on the Cloudflare
  platform.
- Removing a member stays `DELETE /auth/users/{id}`; the full removal workflow is
  later work.

## Upstream case

Any deployment behind an identity-aware proxy has the same gap: the proxy's
sign-in and the application's session are independent, so a borrowed cookie
works. The envelope, the modes and the binding are provider-neutral; the
Cloudflare platform signs the envelope from a validated Access assertion and
implements the admission adapter for an Access group.
